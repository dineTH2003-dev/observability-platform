# Code Review Explanation: Incident Management, Anomaly Page, And ML Anomaly Detection

Last updated: 2026-05-18

This document explains the work done for the incident management page, anomaly page, and AI/ML anomaly detection process. It is written for a code review or evaluation discussion, so it explains the purpose of each connected file, how data moves through the system, and why the implementation is structured this way.

## 1. High-Level Summary

The feature set connects four major areas:

1. Metric ingestion
   - A server-side agent sends host and service metrics to the backend.
   - Backend stores raw metrics in PostgreSQL.

2. ML anomaly detection
   - A Python ML worker converts raw metrics into rollups.
   - It builds features from those rollups.
   - It trains Isolation Forest models and stores model metadata.
   - It scores recent windows with hard rules, rolling baselines, trends, and ML models.

3. Backend anomaly and incident workflow
   - The ML worker sends anomaly events to the backend.
   - Backend deduplicates anomalies, stores ML explanation details, optionally creates incidents, and updates incident timelines.
   - Admin users can see all incidents/anomalies.
   - Non-admin users only see incidents/anomalies assigned to them.

4. Frontend incident and anomaly pages
   - Incident page shows live database incidents, assignment, status actions, and timeline.
   - Anomaly page shows live database anomalies, ML details, score/explanation, feature values, and feedback buttons.

## 2. End-To-End Architecture

```text
Server Agent
  -> POST /api/agent/heartbeat
  -> POST /api/agent/metrics
  -> POST /api/agent/services
  -> PostgreSQL raw data
       servers
       services
       server_metrics
       service_metrics

Python ML Worker
  -> reads raw metric tables
  -> writes rollup tables
       server_metric_rollups_1m
       service_metric_rollups_5m
  -> trains models
       ml_models
       ml/artifacts/*.joblib
  -> scores recent windows
  -> POST /api/ml/anomalies

Backend Anomaly Service
  -> validates ML anomaly payload
  -> deduplicates by fingerprint
  -> checks maintenance/deployment suppression
  -> writes anomalies
  -> writes anomaly_ml_details
  -> creates incidents for high/critical non-suppressed anomalies
  -> writes incident_timeline

Frontend
  -> GET /api/incidents
  -> GET /api/anomalies
  -> GET /api/anomalies/:id
  -> PATCH incident status/assignment
  -> POST anomaly feedback
```

## 3. Main Database Tables

### `users`

Stores application users.

Important columns:

- `id`: user UUID.
- `email`: login email.
- `role`: used for authorization. Admin users see all data; other users see assigned data.
- `is_active`: used when assigning engineers.

### `servers`

Stores monitored hosts.

Important columns:

- `server_id`: primary key.
- `hostname`, `ip_address`, `environment`: entity context.
- `server_status`: health status derived from recent metrics.
- `agent_status`: whether the agent is active/inactive.
- `last_discovered_at`: last heartbeat/discovery time.

### `services`

Stores services discovered on a server.

Important columns:

- `service_id`: primary key.
- `server_id`: parent server.
- `application_id`: optional application relation.
- `name`, `command`, `process_id`, `technology`: service/process details.
- `status`: `RUNNING`, `STOPPED`, `ERROR`, or `UNKNOWN`.

### `server_metrics`

Stores raw host metric samples.

Important columns:

- `server_id`
- `cpu_usage`
- `memory_usage`
- `disk_usage`
- `thread_count`
- `recorded_at`

This is raw ingestion data. It is not ideal for direct ML scoring because individual rows can be noisy.

### `service_metrics`

Stores raw service metric samples.

Important columns:

- `service_id`
- `cpu_usage`
- `memory_usage`
- `recorded_at`

### `server_metric_rollups_1m`

Stores 1-minute server metric windows generated by the ML worker.

Purpose:

- Convert raw host samples into stable ML/scoring windows.
- Store min/max/avg/last values.
- Track missing samples.

### `service_metric_rollups_5m`

Stores 5-minute service metric windows.

Purpose:

- Service discovery runs less frequently than server metrics.
- 5-minute windows reduce noise and are better for model training.

### `ml_models`

Stores current ML model registry.

Important columns:

- `model_id`: UUID.
- `entity_type`: `server`, `service`, `application`, or `global`.
- `entity_id`: entity-specific model target.
- `metric_group`: for example `server_resource` or `service_resource`.
- `algorithm`: currently `isolation_forest`.
- `feature_schema`: feature names used by the model.
- `parameters`: model configuration such as contamination and estimator count.
- `thresholds`: score thresholds.
- `artifact_uri`: path to the serialized `joblib` model.
- `status`: `shadow`, `active`, `retired`, or `failed`.
- `metrics`: training row count and feature count.

### `ml_models_legacy`

The previous local database already had an older incompatible `ml_models` table. The migration preserves those older rows by renaming that table to `ml_models_legacy`.

Purpose:

- Avoid data loss.
- Allow the current worker to use the new schema safely.

### `anomalies`

Stores anomaly events shown on the Anomalies page.

Important columns:

- `anomaly_id`
- `server_id`, `service_id`, `application_id`
- `anomaly_type`
- `severity`
- `title`
- `description`
- `metric_value`
- `threshold`
- `status`
- `incident_id`
- `detected_at`
- `resolved_at`

### `anomaly_ml_details`

Stores explainability details for ML-created anomalies.

Important columns:

- `anomaly_id`
- `model_id`
- `entity_type`
- `detector_name`
- `score`
- `confidence`
- `window_start`, `window_end`
- `expected_value`, `lower_bound`, `upper_bound`
- `feature_values`
- `reason_codes`
- `fingerprint`
- `suppression_reason`

This table keeps the existing `anomalies` table clean while still allowing rich ML metadata.

### `anomaly_feedback`

Stores user feedback from the Anomalies page.

Labels:

- `true_positive`
- `false_positive`
- `expected_change`
- `duplicate`
- `unknown`

This feedback is used for model evaluation and later threshold tuning/retraining.

### `incidents`

Stores incident lifecycle records.

Important columns:

- `incident_id`
- `incident_number`
- `title`
- `description`
- `severity`
- `status`
- `assigned_to`
- `acknowledged_at`
- `resolved_at`
- `created_at`
- `updated_at`

### `incident_timeline`

Stores append-only incident lifecycle events.

Examples:

- incident created
- assigned to engineer
- acknowledged
- resolved

This is important for auditability.

## 4. Incident Management Backend

### `backend/src/routes/incident.routes.js`

Purpose:

- Defines the HTTP API routes for incident management.
- Applies JWT authentication.
- Applies admin-only authorization for assignment.

Routes:

- `GET /api/incidents`
  - List incidents.
  - Admin sees all.
  - Engineer sees assigned incidents only.

- `POST /api/incidents`
  - Creates an incident from anomaly-like data.

- `GET /api/incidents/engineers`
  - Returns users who can be assigned.

- `GET /api/incidents/:id`
  - Gets one incident with linked anomalies and timeline.

- `PATCH /api/incidents/:id/assign`
  - Admin-only.
  - Assigns an engineer to the incident.

- `PATCH /api/incidents/:id/acknowledge`
  - Marks incident as acknowledged.

- `PATCH /api/incidents/:id/resolve`
  - Marks incident as resolved.

### `backend/src/controllers/incident.controller.js`

Purpose:

- Converts HTTP requests into service calls.
- Reads request params/body/user.
- Sends JSON responses.
- Handles errors with HTTP status codes.

Main functions:

- `getIncidents(req, res)`
  - Calls `incidentService.getIncidents(req.user)`.
  - Uses the authenticated user's role/user id.

- `getEngineers(req, res)`
  - Returns assignable active users.

- `getIncidentById(req, res)`
  - Loads one incident by id.

- `createIncident(req, res)`
  - Creates an incident and linked anomaly from request body.

- `assignEngineer(req, res)`
  - Uses `req.user.userId` as the actor in the timeline.

- `acknowledgeIncident(req, res)`
  - Marks work started by the assigned engineer.

- `resolveIncident(req, res)`
  - Marks the incident fixed.

### `backend/src/services/incident.service.js`

Purpose:

- Contains incident business logic.
- Keeps controller thin.
- Coordinates multiple database models.

Important behavior:

- `createIncidentFromAnomaly(anomalyData)`
  - Creates an incident row.
  - Creates an anomaly row.
  - Links anomaly to incident.
  - Adds timeline event.

- `getIncidents(user)`
  - If user role is `admin`, returns all incidents.
  - Otherwise returns only incidents assigned to `user.userId`.

- `assignEngineer(incidentId, engineerId, actorId)`
  - Validates engineer exists and is active.
  - Updates `incidents.assigned_to`.
  - Adds timeline event.
  - Updates linked anomaly status to `assigned`.

- `acknowledgeIncident(incidentId, actorId)`
  - Requires incident to be `open`.
  - Requires incident to be assigned first.
  - Sets `acknowledged_at`.
  - Updates linked anomalies to `acknowledged`.
  - Adds timeline event.

- `resolveIncident(incidentId, actorId)`
  - Sets incident status to `resolved`.
  - Sets anomaly status to `resolved`.
  - Sets anomaly `resolved_at`.
  - Adds timeline event.

### `backend/src/models/incident.model.js`

Purpose:

- Holds SQL queries for `incidents`.

Important functions:

- `create(data, client)`
  - Inserts incident.
  - Optional `client` supports transactions.

- `findAll()`
  - Admin list query.
  - Joins assigned user email.
  - Counts linked anomalies.

- `findByAssignee(userId)`
  - Engineer list query.
  - Only incidents where `assigned_to = userId`.

- `findById(id)`
  - Loads one incident.
  - Adds linked anomalies from the `anomalies` table.

- `assignEngineer(id, userId)`
  - Updates assigned engineer.

- `updateStatus(id, status, timestamps)`
  - Updates incident status and timestamps.

### `backend/src/models/incident_timeline.model.js`

Purpose:

- Stores and reads audit events for incident lifecycle.

Important functions:

- `addEvent(incidentId, actorId, eventType, message, client)`
  - Inserts append-only timeline row.

- `getByIncident(incidentId)`
  - Returns timeline events ordered oldest first.
  - Joins actor email for display.

### `backend/src/middlewares/auth.middleware.js`

Purpose:

- Verifies JWT access token.
- Puts decoded user data into `req.user`.
- Provides `authorize(['admin'])` for admin-only routes.

Important behavior:

- Incident assignment route uses `authorize(['admin'])`.
- Incident listing relies on `req.user.role` and `req.user.userId`.

## 6. Incident Data Flow

### List incidents

```text
Frontend Incidents.tsx
  -> incidentApi.fetchIncidents()
  -> GET /api/incidents
  -> auth.middleware authenticates JWT
  -> incident.controller.getIncidents()
  -> incident.service.getIncidents(req.user)
       admin -> IncidentModel.findAll()
       non-admin -> IncidentModel.findByAssignee(userId)
  -> PostgreSQL
  -> frontend maps and renders cards
```

### Assign incident

```text
Admin clicks Assign
  -> incidentApi.assignEngineer()
  -> PATCH /api/incidents/:id/assign
  -> authenticate + authorize(['admin'])
  -> incident.controller.assignEngineer()
  -> incident.service.assignEngineer()
       validate engineer exists
       update incidents.assigned_to
       update linked anomalies.status = assigned
       insert incident_timeline event
  -> frontend reloads incidents
```

### Acknowledge incident

```text
Engineer clicks Acknowledge
  -> PATCH /api/incidents/:id/acknowledge
  -> service validates incident is open and assigned
  -> incidents.status = acknowledged
  -> anomalies.status = acknowledged
  -> timeline event inserted
```

### Resolve incident

```text
Engineer clicks Resolve
  -> PATCH /api/incidents/:id/resolve
  -> incidents.status = resolved
  -> anomalies.status = resolved
  -> anomalies.resolved_at = NOW()
  -> timeline event inserted
```

## 7. Anomaly Backend

### `backend/src/routes/anomaly.routes.js`

Purpose:

- Defines authenticated anomaly endpoints.

Routes:

- `GET /api/anomalies`
  - List visible anomalies.

- `GET /api/anomalies/:id`
  - Get full anomaly detail.

- `PATCH /api/anomalies/:id/status`
  - Update anomaly status.

- `POST /api/anomalies/:id/feedback`
  - Store user feedback.

### `backend/src/controllers/anomaly.controller.js`

Purpose:

- HTTP layer for anomaly page requests.
- Passes `req.user` into service layer so role-based visibility is enforced.

Important functions:

- `getAll`
  - Reads filters from query string.
  - Calls `AnomalyService.getAnomalies(filters, req.user)`.

- `getById`
  - Calls `AnomalyService.getAnomalyById(id, req.user)`.

- `updateStatus`
  - Calls `AnomalyService.updateStatus(id, status, req.user)`.

- `addFeedback`
  - Calls `AnomalyService.addFeedback(id, body, req.user)`.

### `backend/src/services/anomaly.service.js`

Purpose:

- Contains anomaly business logic.
- Handles role-based visibility.
- Handles ML anomaly ingestion.
- Handles feedback validation.

Important behavior:

- `getAnomalies(filters, user)`
  - Admin users can see all anomalies.
  - Non-admin users are scoped to anomalies whose linked incident is assigned to their user id.

- `getAnomalyById(id, user)`
  - Loads detail.
  - Runs access check.
  - Non-admin users cannot open unassigned or other users' anomalies.

- `updateStatus(id, status, user)`
  - Validates status.
  - Checks access before update.

- `addFeedback(id, data, user)`
  - Checks access.
  - Validates feedback label.
  - Inserts feedback with `created_by = user.userId`.

- `createFromMlDetection(payload)`
  - Used by the ML worker.
  - Normalizes incoming payload.
  - Builds deterministic fingerprint.
  - Deduplicates existing anomaly by fingerprint.
  - Checks maintenance/deployment suppression.
  - Creates anomaly and ML detail in a transaction.
  - Creates incident for high/critical detections unless suppressed or disabled.

### `backend/src/models/anomaly.model.js`

Purpose:

- Holds SQL for anomaly persistence and retrieval.

Important functions:

- `create(data, client)`
  - Inserts row into `anomalies`.

- `createMlDetails(anomalyId, data, client)`
  - Inserts linked ML explanation row.

- `findDuplicateByFingerprint(fingerprint)`
  - Used to suppress duplicate anomaly rows.

- `findAll({ status, severity, assignedToUserId, limit })`
  - Returns anomaly list with server/service/application names.
  - Joins incident assignment and assigned engineer email.
  - Joins ML detail fields such as detector, score, confidence, reason codes.
  - Filters by assignment for non-admin users.

- `findById(id)`
  - Returns one anomaly with full ML details and feedback history.

- `updateStatus(id, status, resolvedAt)`
  - Updates anomaly lifecycle status.

- `addFeedback(...)`
  - Inserts user feedback.

## 10. Anomaly Data Flow

### List anomalies

```text
Frontend Anomalies.tsx
  -> anomalyApi.fetchAnomalies()
  -> GET /api/anomalies
  -> auth.middleware authenticates JWT
  -> anomaly.controller.getAll()
  -> anomaly.service.getAnomalies(filters, user)

       non-admin -> assignedToUserId = user.userId
```

### Load anomaly detail

```text
User clicks anomaly card
  -> selectedAnomaly changes
  -> frontend calls fetchAnomalyById(id)
  -> GET /api/anomalies/:id
  -> service checks access
  -> model loads anomaly, ML details, feedback history
  -> frontend renders detail panel
```

### Give feedback

```text
User clicks True / False / Expected / Duplicate
  -> POST /api/anomalies/:id/feedback
  -> auth middleware identifies user
  -> service checks user can access anomaly
  -> service validates label
  -> anomaly_feedback row inserted
  -> frontend reloads detail and list
```

Purpose:

Important functions:

  - Reads `server_metrics`.
  - Groups by server and 1-minute window.
  - Writes `server_metric_rollups_1m`.

- `backfill_service_rollups(conn, hours)`
  - Reads `service_metrics`.
  - Groups by service and 5-minute window.
  - Writes `service_metric_rollups_5m`.

### `ml/app/features/server_features.py`

Purpose:

- Loads server rollups.
- Builds ML features for server models.

Feature examples:

- current averages and last values
- robust z-scores
- deltas over time
- hour of day
- day of week
- weekend flag
- missing count

### `ml/app/features/service_features.py`

Purpose:

- Loads service rollups.
- Joins service/server context.
- Builds service-level ML features.

Feature examples:

- service CPU/memory
- parent server CPU/memory
- service-to-server ratios
- robust z-scores
- 15-minute deltas
- time features
- missing count

### `ml/app/detectors/types.py`

Purpose:

- Defines the `Detection` dataclass.
- Provides `to_payload()` for backend posting.

This makes all detectors return the same structure.

### `ml/app/detectors/hard_rules.py`

Purpose:

- Deterministic safety rules.

Examples:

- server CPU >= 95%
- server memory >= 95%
- server disk >= 90%
- service CPU >= 95%
- service memory >= 95%
- missing server metric samples

Hard rules are important because obvious danger should not wait for ML confidence.

### `ml/app/detectors/rolling_baseline.py`

Purpose:

- Detects when a metric is unusual compared to that entity's recent baseline.

Method:

- Uses rolling median and IQR.
- Uses robust z-score.
- Creates detections when z-score is high.

This catches entity-specific unusual behavior even when the value does not cross a global hard threshold.

### `ml/app/detectors/isolation_forest.py`

Purpose:

## 13. AI/ML Process

The anomaly detection design is a hybrid system:

1. Hard rules
   - Catch obvious dangerous values immediately.
   - Example: CPU or memory above 95%.

2. Rolling baseline detector
   - Learns recent normal range per entity.
   - Detects unusual values relative to that entity's own behavior.

3. Isolation Forest
   - Learns multivariate normal behavior.
   - Detects unusual combinations of metrics.

4. Trend detector
   - Catches slow movement toward failure, especially disk growth.

This hybrid design is safer than using only one ML model because:

- Rules catch clear resource danger.
- Baselines adapt to entity-specific behavior.
- Isolation Forest catches combinations.
- Trends catch slow failures.

## 15. Feedback And Model Optimization

Feedback flow:

```text
User reviews anomaly
  -> clicks True / False / Expected / Duplicate
  -> frontend POST /api/anomalies/:id/feedback
  -> backend validates access and label
  -> anomaly_feedback row inserted
  -> evaluation job summarizes feedback
```

Important point:

Feedback does not instantly retrain the model. The current model is unsupervised Isolation Forest, so feedback is used for evaluation and later tuning.

How feedback changes future behavior:

- Many `false_positive` labels:
  - Raise score threshold.
  - Lower contamination.
  - Add persistence requirement.
  - Keep model in shadow.

- Many `true_positive` labels:
  - Keep thresholds.
  - Consider promoting model from `shadow` to `active`.

- Many `expected_change` labels:
  - Add maintenance/deployment suppression windows.
  - Exclude those periods from training/evaluation.

- Many `duplicate` labels:
  - Improve fingerprinting/cooldown/correlation logic.

## 19. Review Talking Points

Use this summary during review:

1. The incident page is no longer static. It reads incidents from the backend and supports assignment, acknowledgement, resolution, details, and timeline.

2. Role-based access exists in the backend. Admins see all incidents/anomalies, while non-admin users see only assigned records.

3. The anomaly page is connected to the database. It shows live anomaly rows, detail data, ML metadata, feature values, and feedback history.

4. Feedback is stored in `anomaly_feedback`. It is used to evaluate model quality and guide future threshold tuning/retraining.

5. The ML pipeline is separate from the Node backend. Node owns APIs and incident workflow; Python owns data science, feature engineering, and model scoring.

6. The anomaly detection strategy is hybrid, not only ML. It combines hard thresholds, rolling baselines, trend detection, and Isolation Forest.

7. Models are in shadow mode because we need continuous data and feedback before automatic incident creation is fully trusted.

8. Deduplication uses an anomaly fingerprint so repeated detections for the same entity/metric/window do not create duplicate incidents.

9. ML explainability is preserved through `anomaly_ml_details`: detector name, model id, score, confidence, bounds, feature values, reason codes.

10. The architecture is designed to grow: later we can add request rate, error rate, latency, deployment windows, maintenance windows, and feedback-based retraining.

## 20. Known Gaps And Future Work

Current limitations:

- Feedback is stored and summarized, but automatic retraining from feedback is not implemented yet.
- The Anomalies page supports text feedback labels but does not yet collect detailed comments from the UI.
- Service health metrics are still limited to CPU and memory.
- No latency/error-rate/request-rate metrics yet.
- Scheduling is manual CLI right now; production should run jobs through cron, systemd timers, or a worker scheduler.
- Models should remain `shadow` until 7 to 14 days of continuous recent data and enough feedback are collected.
- Frontend build currently shows unrelated existing warnings about notification/sonner exports and bundle size.
